# NUMBER×RUSH Vol.58｜Variety未保存イベントの安全な永続化・復旧設計（暫定）
日付: 2026-10-23

## 目標
Vol.57のメモリ内再送キュー（上限128件）はリロードで消失する。ゲームのスコア・盤面・判定と独立したまま、**同じanswerIdを保持して再起動後に安全に再送**できるようにする。

## 信頼境界・原則
1. 既存のVariety履歴v2は唯一の正本。再送待ち領域は別名前空間 `number-rush:variety-pending:v1`。v2の記録を直接書き換えない。
2. すべての読み出し・マイグレーション・追加・削除は同じoriginのWeb Locks排他ロック（新規pending専用ロック）を必須とする。Web Locks非対応では**永続化も復旧も停止**し、ゲームは続行する。
3. イベントは`answerId`、`outcome`、`consumedTileCount`、`schemaVersion=1`のみの最小データ。個人情報・セッションの認証情報・問題の回答内容は保存しない。
4. `MISS`は保存対象外。CLEARの消費枚数は1〜6、IDは正規表現・長さで検証。
5. 再送は**必ず同じanswerId**で既存`committer.retry(originalEvent)`を使用。保存成功確認後にのみpendingから削除。
6. 再送成功とpending削除は別ストレージ操作で原子的ではない。削除前にクラッシュしても、v2履歴の冪等保存により重複を吸収する。ただし既存履歴が保持するID範囲を超えた後の古い再送ではexactly-onceは保証できない。
7. 同じIDで異なるイベント内容を発見したら破損・衝突として隔離。上書き・自動修復しない。
8. キューは上限128件。容量超過・QuotaExceeded・破損・権限拒否の場合は**fail closed**で警告し、古いpendingを勝手に破棄しない。
9. 再起動時はpendingスキーマを検証し、Web Locks内で復旧。壊れたJSONや未知バージョンは元データを保持して読み出し拒否。ユーザーの明示操作なしに消去しない。
10. マルチタブではpendingロックとVariety履歴ロックの二重ロックを同時保持しない。pending読み出し→履歴ロック下で再送→pendingロック下で削除の順。別タブで同一IDを再送しても履歴の冪等性に依存する。

## 失敗窓の設計
- **回答ID発行→pending書込→履歴書込→pending削除**というwrite-ahead方式を検討する。履歴書込に先行してpending保存できなければ再起動後の復旧は保証しない。
- Vol.56の現行`committer.commit()`は内部で回答IDを生成し直ちに履歴へ書くため、外側のVol.57コーディネータから後付けで完全なwrite-ahead原子性を実現できない。**次の実装段階で回答ID生成と永続化の境界をリファクタリングする必要がある**。
- 保留イベントの追加に失敗したときはゲーム進行を止めず、HUDに「統計未保存・再起動で消失する可能性」を表示する。
- 保存成功後の削除失敗はpendingを残し、次回の冪等再送で解消する。
- 保存先が共有端末である可能性があるため、個人情報を保存しない。ブラウザストレージを安全な秘匿保管庫とはみなさない。

## 状態遷移
`EMPTY -> PENDING -> WRITTEN -> REMOVED`
- `PENDING -> PENDING`: 失敗・オフライン・ロック非対応。
- `PENDING -> QUARANTINED`: 破損・ID衝突・未知バージョン（原本保持）。
- `WRITTEN -> PENDING`: 削除失敗で残るが、次回同IDの冪等再送で再確認。

## 検証すべきテスト
- 正常時の追加→保存→削除。
- 履歴書込前クラッシュ→再起動復旧。
- 履歴書込後削除前クラッシュ→重複計上なし。
- 複数タブ同一ID並行再送。
- ロック非対応・ストレージ容量不足・破損JSON・未知スキーマ・ID衝突。
- 128件満杯、順序保持、古いIDが履歴の冪等保持窓から消えたケース。

## 実装状況
**本Vol.58は設計のみ**。Vol.57のメモリ内キューは既存のまま。永続pendingストアとクラッシュ復旧は未実装であり、再起動後の保存を保証しない。
