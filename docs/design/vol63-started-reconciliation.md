# Vol.63 設計：started不確定イベントの安全な照合・解除
**暫定設計・自動解除は実装しない。**

## 背景
Vol.62はpending→台帳started→20件履歴→台帳saved→pending ackの順序。クラッシュ後のstartedは履歴に記録済みかどうかを20件窓だけでは判断できない。古いIDを無条件に再送すると二重計上が起き得る。

## 原則
1. **照合は証拠主義**。単なる時刻経過・20件履歴からの消失・ユーザーのボタン操作だけではstartedをsaved/未保存と決めない。
2. すべての照合・台帳更新・pending操作をVol.61の`RECOVERY_LOCK_V61`で直列化する。既存writerも同じロックを使うことが前提。
3. 追加の**永続コミットジャーナル**（回答ID、outcome、消費枚数、履歴反映を確認できる単調シーケンス、チェックサム）を設計し、回答履歴保存と同じ永続トランザクション境界に置く。localStorageの複数キー更新には原子的トランザクションがないため、別キーのジャーナルだけでは証明にならない。将来はIndexedDB単一readwriteトランザクションに統合する案を優先比較。
4. startedの状態は`unresolved`として隔離。照合結果が`committed`と証明できればsavedに更新→pending ack。未コミットが**確実に証明できる**場合だけ元IDで再処理する。証拠不十分なら保留。
5. UIは`未確定の記録 N件（ゲーム進行には影響しません）`と表示し、診断情報のエクスポート・再照合だけ提供。ユーザー操作で「記録済み」「破棄」を無証拠に選ばせない。
6. データ破損・台帳上限・Web Locks非対応時は書込を停止し、元データを上書きしない。照合履歴は監査ログに記録（個人情報は含めない）。
7. 同一回答IDを跨いで再利用しない。異なるタブが同一answerKeyで別answerIdを生成する問題は別途**グローバルな回答キー台帳**で解決する必要がある。

## 安全な段階的導入
A. 現行localStorage上ではstartedを隔離し、件数・原因を表示する読み取り専用アダプタを先行。
B. IndexedDBで回答イベント・ID台帳・表示用履歴を単一トランザクションで更新するプロトタイプを実装。
C. 故障注入（各書込段階で強制停止）、複数タブ同時更新、履歴20件超過、再起動の試験を実施。
D. データ移行のロールバック計画を用意し、検証完了後にのみ自動照合・解除を有効化。

## 非保証事項
Vol.63時点で不確定startedの自動照合・解除機能は未実装。exactly-once保証は未達。安全優先で保留するため統計欠落はあり得る。
